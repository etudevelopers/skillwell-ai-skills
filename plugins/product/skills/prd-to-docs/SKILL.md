# PRD to documentation

Convert a PRD into audience-appropriate documentation.

## Steps

1. **Confirm the audience and format.** Ask which of these is wanted (default: stakeholder brief):
   - **Stakeholder brief**: one page, problem, solution, impact, timeline, risks
   - **Release notes**: user-facing, benefit-led, grouped as New / Improved / Fixed
   - **Feature guide**: how-it-works for end users or support, with steps
2. **Read the whole PRD.** If it is not provided, ask for the file or pasted text.
3. **Draft** in the chosen format using plain language for the target audience. Remove internal jargon, ticket numbers and implementation detail unless the audience is technical.
4. **List open items**: anything in the PRD that was unclear, undecided or contradictory, so the product owner can resolve it before publishing.

## Rules

- Only state what the PRD supports. Mark anything inferred as `[confirm]`.
- Keep dates, names and numbers exactly as in the PRD.
- Do not include confidential commercial details (pricing, customer names) unless the PRD content is explicitly for that audience.
